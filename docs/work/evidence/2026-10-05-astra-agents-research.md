# What changes when the workers are agents

Independent source reading, October 5, 2026, America/New_York. Written before opening the incumbent method/design documents. The question is not whether agents can code, but when their coordination and evaluation improve useful outcomes after all costs are counted.

## Findings that change the plan

Use a real project outcome as the unit of progress. Keep the smallest execution arrangement that can pass its acceptance test. Parallelize genuinely independent questions, not every implementation step. Preserve task state outside the conversation, but do not mistake a fresh context or a different model vendor for independent evidence. Put the hardest uncertainty in front of actual users or executable observations early. These are recommendations inferred from the sources below, not a validated package for this repository.

## What is genuinely different

Agents make producing an implementation or a persuasive justification cheap relative to checking whether it should exist. That shifts the limiting resource toward problem selection, integration, independent verification and owner attention. This is an inference about this workflow, not a claim that machine labor is free. Subscription pricing does not eliminate context limits, opportunity cost, review load or elapsed time.

An agent does not necessarily have zero memory: files, transcripts and resumable sessions are memory. The failure is that memory can be incomplete, stale, inaccessible or not read. Fix the retrieval/checkpoint boundary, not the agent's personality. Preserve the current artifact, failed attempts and unresolved claim; do not reload the whole organizational history each time.

Independent model samples are not independent engineering observations. Diverse providers can help, but agreement by itself is weak support. Prefer a reviewer who reconstructs the acceptance case, examines actual behavior, and states a counterexample over three judges choosing the better prose. Human experts can also share assumptions; a user doing the real task is a different evidence source.

Agents have no organizational career stake comparable to a long-tenured maintainer. Do not infer malicious intent from that; design authority and evidence boundaries instead. The executor may suggest and test changes, but cannot change the success test, bless its own boundary violation or declare its missing tests irrelevant. Genuine safe redesign can remove the dependency that triggered a guard; rephrasing the same denied action cannot supply authorization.

For the local productivity trial, report active owner minutes, elapsed completion time, retries/rework, quality failures and machine cost with coverage. The four existing goal measures remain available, but none should be interpreted as the purpose of the product. A cheaper rejected feature is not a successful outcome. A zero-rework observation is immature until its follow-up window elapses.

## Counterevidence and open questions

The best architecture may still include durable orchestration when a real task repeatedly crosses machines or outlives sessions. Removing it can move failure handling into Ben's memory. A single agent is a baseline, not an ideology. Neither the local incident sequence nor the papers establish an optimal agent count, review-round limit, number of artifacts or cadence for this project. Those defaults need a local trial and explicit reconsideration when they fail.
