**NEEDS_FIXES**

This is a source-only review of the packet at manifest head `d6eea82`. I made no writes and ran nothing. The scheduler files aren't in the packet, so the claims about IgnoreNew, oneshot and launchd serialization are still unverified.

**1. BLOCKER: the dynamic import can deadlock.** `note-flush.mjs:1133` runs the whole CLI inside a top-level `await main()`. The proposal (proposal.md:54) imports `decisions-pickup.mjs` from inside `main()`. That file imports `note-send.mjs` (`decisions-pickup.mjs:18`), which imports `note-flush.mjs` (`note-send.mjs:95`). That is the same module that is still paused on its top-level await. Under ES module rules the new import waits for `note-flush` to finish, and `note-flush` is waiting for the import, so it never resolves. Node would then exit with code 13, leaving the unsettled await. Pickup never runs and "exit 0 always" breaks. I'm confident in this, but it needs a real process to prove. *Fix:* change the entry point to `main().then((c) => { process.exitCode = c; })`. Add a test that spawns the real `node note-flush.mjs` with a sealed home, a registration file and a stub reader, and checks exit 0 and that pickup ran.

**2. HIGH: failures stay silent.** proposal.md:56 says success is silent and allows only four stderr codes. But `pickupOnce` *returns*, rather than throws, `UNKNOWN`, `NEEDS_RECONCILIATION`, `PENDING_MANUAL_HANDOFF`, `INVALID` and `ORPHAN_CAPTURE` (`decisions-pickup.mjs:593, 709-716, 856-861, 895`). The spec would count all of these as silent successes. Separately, a claim left behind by a crash or host sleep is never cleared (`decisions-pickup.mjs:142-156`), so that page fails every cycle, forever. Scheduled-task stderr may simply be thrown away (unknown per host). *Fix:* map every result status to a fixed allowlist of codes. Record the latest one as a single field added to the existing `flush-last.json`: `pickup: {at, code, ordinal}`. Write it after pickup, overwrite it each time, and never include paths or page text. Add `PICKUP_CLAIM_HELD`. `--status --json` then shows it with no new state file, and `--status` keeps its exit behaviour. That means relaxing the "must not alter heartbeat" rule to "one added field only".

**3. HIGH: the fairness claim isn't supported.** proposal.md:45 and :81 say each entry gets exactly one turn per N minutes. With IgnoreNew, a run that spills past its minute drops the next slot, and a flush can run up to 100 s (`note-flush.mjs:78`). So the entry right after a slow entry loses its turn every cycle, and runs that settle into a 2-minute rhythm starve every other entry. *Fix:* pick the entry with `crypto.randomInt(count)` (injectable in tests), say "expected" rather than guaranteed fairness, and drop "exactly once per cycle".

**4. MEDIUM: duplicate pages across projects.** Receipts and claims are keyed by page only (`decisions-pickup.mjs:101-109`). proposal.md:32 only rejects duplicate `(repo,page)` pairs. So `(A,P)` and `(B,P)` both pass, and B then gets a silent `PENDING_MANUAL_HANDOFF` forever (`:709`). *Fix:* reject a duplicate normalized page, and separately a duplicate canonical repo.

**5. MEDIUM: the time budgets are wrong or have no limit.** `--no-type` is really passed (`decisions-pickup.mjs:471`). But it skips note-send's drain entirely (`note-send.mjs:319-320`, compared with `:326-334`), so the "3,000 ms drain" in proposal.md:54 isn't real. `gitRunner` is an `execFileSync` with no timeout (`transport.mjs:412-416`). It runs in pickup (`:570-573`) and twice in note-send (`:271`, `:375`). Reading the whole ledger has no size limit either (`note-send.mjs:458`, `decisions-pickup.mjs:483-517`). *Fix:* delete "roughly 48 seconds". State that only the reader is bounded (15 s) and that git and filesystem time are unknown and unbounded.

**6. MEDIUM: three different home directories.** note-flush takes its home from `--home` or `os.homedir()` (`:465`). Pickup uses `AGENTS_HOME` (`:82-84`). The note-send call inside pickup gets empty `sendDeps` (`:673`), so it uses `os.homedir()` (`note-send.mjs:216`). *Fix:* skip pickup when `--home` is given, or when `AGENTS_HOME` resolves to anything other than `<homedir>/.agents`, and report `PICKUP_CONFIG_INVALID`.

**7. MEDIUM: the reader is unattended code execution.** A timer runs the registered reader with the host's Notion credentials. If that file sits in a Git checkout, a pull can silently change it. *Fix:* reject a reader that is a symlink, or that sits inside any registered or transport repo or any Git checkout (reuse `detectedGitRoot`).

**8. LOW:**
- `page` should be required to reduce to a 32-hex id. Otherwise `normalizedPage` returns the raw string (`:69`), and that string goes straight into the reader's arguments.
- A `WAITING_OWNER` round gets bound to the registered owner (`:913-935`). That contradicts proposal.md:35 ("only a fresh round").
- The CLI can't tell a timer run from someone running `note-flush` by hand (`note-flush.mjs:1004-1007`), so manual runs will also read Notion. The spec should say so.

**9. Recorded vs. woken vs. acted on.** The spec should keep these three apart:
- **Recorded:** `RECORDED` only means the note is in the ledger and a wake-up entry is queued (`note-send.mjs:683-719`).
- **Woken:** the owner is woken on the *next* flush pass through their inbox. If they have no inbox, the entry expires after 48 h with a BLOCKED line in Ben's inbox (`note-flush.mjs:657-671`). If the owner slug is unknown on the host, it's dropped after 10 minutes with a BLOCKED line (`:584-630`). That existing mechanism already covers wake-up failures, so nothing new is needed there.
- **Acted on:** only `account` records that the owner did the work. Nothing in this design detects or claims it.

The shape of the proposal is right: one private registration file, one call after the flush, and reuse of `pickupOnce`. It is not ready to build until #1–#3 are fixed and the required-tests section covers #4–#7.
