## m2 (minor) — fixed: `--out` is now resolved and control-character-refused before any write

Finding: a relative `--out` landed unresolved into the collect job's own argv (so a relative value
would be interpreted against the repo's own `WorkingDirectory=` at run time — writes under the repo
tree, breaking C1's "no writes under the repo"), and a literal newline inside `--out` survived
`systemdQuote` far enough to add a second directive line to the generated systemd unit.

Fix applied exactly as the reviewer's mechanical recipe (scripts/install-janitor-timer.mjs, the
`--out` handling block, now ~:582-598):
```
const outGiven = argv.includes("--out");
const outRaw = parseArgFlag(argv, "--out");
if (outRaw !== null && /[\u0000-\u001f\u007f]/.test(outRaw)) {
  refusals.push(`--out must not contain control characters, got ${JSON.stringify(outRaw)}`);
}
const outFlag = outRaw === null ? null : path.resolve(outRaw);
```
New test, "C2 review round 1, m2: --out is resolved to an absolute path ... and a control character
... is refused outright": a real install with `--out rel` produces a service unit whose ExecStart
contains `--out <path.resolve("rel")>` (asserted against the same `path.resolve` the test computes,
not a hard-coded absolute path, so it holds on any host); `--out "out\nExecStartPost=pwn"` exits 1
with `"--out must not contain control characters"` in the refusals and writes nothing
(`~/.agents` does not exist afterward). The pre-existing `withOut` test (absolute `/tmp/out`) is
unaffected: `path.resolve` of an already-absolute path is a no-op.
