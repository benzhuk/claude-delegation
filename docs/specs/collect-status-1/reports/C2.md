## N1 (major) — fixed: Windows twin of M1, the collect job could replace/delete the janitor's live scheduled task by name

Finding (reviewer): Task Scheduler has ONE task-name namespace, but each job keeps its task XML in
a different directory (`~/.agents/janitor/<name>.task.xml` vs `~/.agents/collect/<name>.task.xml`,
install-janitor-timer.mjs, pre-round-3 :681/:723). The marker/foreign-file ownership check only
ever reads the CURRENT job's own artifact path, so it never sees the other job's file, and a
same-`--name` install or `--remove --enable` reached the other job's live task by name alone —
measured by the reviewer on `platform: "win32"` with injected exec: janitor installed with
`--enable`, then `--enable --job collect-status --to skills-fable --name janitor-record` ran
`schtasks /Create /TN janitor-record /XML <home>/.agents/collect/janitor-record.task.xml /F`,
replacing the janitor's live task; `--remove --enable --job collect-status --name janitor-record`
ran `schtasks /Delete /TN janitor-record /F`, deleting it; the reverse direction (`--remove
--enable --name collect-status` against a collect install) deleted the collect job's task the
same way. Linux and darwin already refused these (marker check works there because the unit/plist
file IS the scheduler identity).

Fix applied exactly as the reviewer's mechanical patch (install-janitor-timer.mjs, now :672-682,
immediately before `const result = { action: ... }`): on `platform === "win32"` only, before any
write or exec, check whether the OTHER job already owns a same-named task XML
(`~/.agents/<janitor|collect>/<name>.task.xml`); if it exists, push a refusal
(`refusing: --name <name> is already the <other-job> job's scheduled task (<path>); pick another
--name`). Pushed onto the shared `refusals` array, so it is read by both the install-path and
`--remove`-path refusal checks below it, matching the reviewer's "install and remove alike"
requirement, at zero exec calls (the refusal fires before any `exec(...)` call site).

New test: "C2 review round 2, N1: on Windows, --name reuse across jobs is refused before any
write or exec (Task Scheduler's single task-name namespace)" (test.mjs). Covers all three of the
reviewer's measured commands, on `platform: "win32"` with an injected `exec` that records every
call:
- Janitor `--enable`, then `--enable --job collect-status --to skills-fable --name janitor-record`:
  now exit 1, zero exec calls, janitor's task.xml and installed.json byte-identical to before,
  no collect task.xml written.
- `--remove --enable --job collect-status --name janitor-record`: exit 1, zero exec calls,
  janitor's task.xml still present and byte-identical.
- Reverse direction (collect job installed under its own default name, then default-job
  `--remove --enable --name collect-status`): exit 1, zero exec calls, collect job's task.xml
  byte-identical.

Mutation proof: reverted the `if (platform === "win32")` guard to
`if (false && platform === "win32")` (disabling the new check) and reran the gate — 47/48, the new
N1 test's reverse-direction assertion fails (`0 !== 1`, expected exit 1 got exit 0). Restored;
gate back to 48/48.

Residual, named as the reviewer asked: a live task whose XML was deleted by hand cannot be
detected without querying `schtasks` — this installer never shells out to query scheduler state
(text-generation only; no live `schtasks`/`launchctl`/`systemctl` execution is possible on this
host, same standing caveat as every prior round).

## N2 (major) — fixed: on macOS, `--remove --job collect-status` without `--to` threw an uncaught TypeError

Finding (reviewer): `launchdPlist` (pre-round-3 :313) assumed every scheduled-command argv element
is already a string: `.map((a) => a.replace(/'/g, "'\\''"))`. The `--remove` path calls it with
`to: null` (the collect job's `--to` is not required for `--remove`, per round-1's m3/K3 fix), so
the collect job's argv contains a literal `null`, and `.replace` on `null` throws
`TypeError: Cannot read properties of null (reading 'replace')`, uncaught — prints a stack,
removes nothing, leaves the plist and `~/.agents/collect/installed.json` in place. `systemdQuote`
(:173, `String(arg)`) and the Windows generator (plain template-literal quoting) already tolerated
null, which is why linux and win32 didn't hit this.

Fix applied exactly as the reviewer's mechanical patch (install-janitor-timer.mjs:313):
`.map((a) => a.replace(...))` → `.map((a) => String(a).replace(...))`, the same coercion
`systemdQuote` already used.

New test: "C2 review round 2, N2: --remove --job collect-status without --to must not throw on
darwin or win32 (launchdPlist argv coercion)" (test.mjs). For both `platform: "darwin"` and
`platform: "win32"`: installs the collect job with `--to`, confirms the artifact and
installed.json exist, then runs `--remove --job collect-status` with no `--to` and asserts exit 0
with both files gone. (win32 was already null-tolerant via a different code path —
`windowsTaskXml` quotes with a plain template literal, never `.replace` — the reviewer asked for
both platforms as a regression guard; both pass with the fix.)

Mutation proof: reverted `String(a).replace(...)` back to `a.replace(...)` and reran the gate —
47/48, the new N2 test fails with exactly the predicted
`TypeError: Cannot read properties of null (reading 'replace')` at install-janitor-timer.mjs:313
inside `launchdPlist`, called from `main`. Restored; gate back to 48/48.
