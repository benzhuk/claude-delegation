### M1 (major): the collect job shares the janitor's marker, so it can overwrite or remove the janitor's units (K3 not met)

contracts.md K3: "`--remove --job collect-status` removes only files carrying the collect job's
own marker line". K1: "The janitor file keeps its bytes whatever the collect job does." The
change has one `MARKER` (install-janitor-timer.mjs:71), used by both jobs (`markerLine()` at :78,
artifact markers at :684-685, :695, :703). Ownership is decided by `content.includes(MARKER)`
(:357), so a collect-job run treats the janitor's units as its own. The name is the only thing
keeping the jobs apart, and `--name` is accepted in production.

Reproduced on a scratch copy (fresh home, janitor installed first):
- `--job collect-status --to skills-fable --name janitor-record`: exit 0, `updated:
  .../janitor-record.service` and `updated: .../janitor-record.timer`. The janitor's service now
  runs `collect-status.mjs`. `~/.agents/janitor/installed.json` still says
  `"name":"janitor-record","hour":6`, so the J2 wiring check sees a healthy janitor that no longer
  runs.
- `--remove --enable --job collect-status --name janitor-record`: exit 0, `removed:
  .../janitor-record.service`, `removed: .../janitor-record.timer`,
  `ran: systemctl --user disable --now janitor-record.timer`.

The builder's test at test.mjs:~985 ("removes only the collect job's own files") only uses the
default names, so it cannot see this.

Cause: one shared marker string, so "ours" means "made by either job".
Discriminating check: install the janitor, then run `--remove --enable --job collect-status
--name janitor-record`. Today: exit 0 and the janitor units are removed. Fixed: exit 1,
`refusing --remove --enable: foreign (unmarked) file(s) present ... janitor-record.service,
janitor-record.timer`, and nothing is removed.
Fix location: scripts/install-janitor-timer.mjs:71 (constant), :78-84 (`markerLine`), and the
four collect-branch generator marker lines plus the four artifact `marker:` fields.
Simplification: no new check or code path is needed. The existing `readMarked`/foreign-file
refusal already does the work once each job has its own marker. The janitor's marker and bytes
stay exactly as they are.

Fix (mechanical; I prototyped it on a scratch copy and measured the outcome):
1. After :71 add
   `const COLLECT_MARKER = "generated by delegation collect-status installer";`
   The new string must NOT contain `MARKER` as a substring. Otherwise the janitor's
   `includes(MARKER)` would still claim collect files.
2. Replace
   ```
   function markerLine(commentStyle) {
   ```
   with
   ```
   function markerLine(commentStyle, job = DEFAULT_JOB) {
     const m = job === "collect-status" ? COLLECT_MARKER : MARKER;
   ```
   Inside it, change `` `<!-- ${MARKER} -->` `` to `` `<!-- ${m} -->` `` and `` `# ${MARKER}` `` to
   `` `# ${m}` ``.
3. Pass `job` in the generators: `markerLine("hash", job)` in `systemdServiceUnit` (:178), in the
   collect branch of `systemdTimerUnit` (:196; leave the janitor branch at :211 as is),
   `markerLine("xml", job)` in `windowsTaskXml` (:268) and `launchdPlist` (:322). Pass it in the
   artifacts too: `marker: markerLine("hash", job)` at :684 and :685, and
   `marker: markerLine("xml", job)` at :695 and :703.
4. Update the builder's own test at test.mjs:755 and :770 from
   `"# generated by delegation install-janitor-timer\n" +` to
   `"# generated by delegation collect-status installer\n" +`. This is a new C2 test, not a
   pre-existing byte-stability test. Add one regression test that runs both clobber commands above

### m2 (minor): `--out` passes through unresolved and unvalidated (relative path lands in the repo; a newline injects systemd directives)

install-janitor-timer.mjs:576 `const outFlag = parseArgFlag(argv, "--out");` goes straight into
the argv (:135).

- A relative `--out out` is resolved at run time against `WorkingDirectory=<repo>` (the service
  unit). The collector then writes status.json, status.md and previous.json inside the repo
  working tree, which breaks C1's "no writes under the repo".
- `--out $'out\nExecStartPost=/bin/touch /tmp/pwn'` gives (measured, dry-run):
  `ExecStart=... --out "out\nExecStartPost=/bin/touch /tmp/pwn"`, with a real newline. That is a
  second directive line in the unit. `systemdQuote` quotes whitespace but cannot make a newline
  safe. The input is operator-supplied, so this is not a remote vector. `--host` has the same
  pre-existing problem.

Fix: replace
```
  const outFlag = parseArgFlag(argv, "--out");
```
with
```
  const outRaw = parseArgFlag(argv, "--out");
  if (outRaw !== null && /[\u0000-\u001f\u007f]/.test(outRaw)) {
    refusals.push(`--out must not contain control characters, got ${JSON.stringify(outRaw)}`);
  }
  const outFlag = outRaw === null ? null : path.resolve(outRaw);
```
Predicted: the existing `withOut` test (`/tmp/out`, absolute) is unchanged. Add a test that
`--out rel` lands as `path.resolve("rel")` in ExecStart, and that a newline-bearing `--out` exits 1
with nothing written.
