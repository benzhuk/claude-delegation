## Pinned design

1. **The job.** New `scripts/knowledge-triage.mjs`, run by the existing timer installer as a third job: `install-janitor-timer.mjs --job knowledge-triage --hour <H>` (default 5). Windows Task Scheduler on the writer host is the only scheduler this lane installs; on any host whose name is not the writer's the installer refuses `--job knowledge-triage` with exit 2 and the message "knowledge-triage installs only on the writer host <name>" (no do-nothing units anywhere), and the byte-stability tests of the other jobs hold. The installer's marker becomes a per-job table (three cases, not the two-case ternary at install-janitor-timer.mjs:102), so `--remove --job knowledge-triage` touches only this job's files; a test asserts the janitor-record and collect-status files survive a triage remove. State dir `~/.agents/knowledge-triage/`. The Windows task runs only when the user is logged on (interactive token, so the Claude CLI's plan login is available); a logged-off desktop skips the run, logged.
2. **Writer host.** The job reads the one name the skill already uses, BEN-DESKTOP, from the skill's writer paragraph, compares `os.hostname()`, and on any other host exits 0 with "not the writer host: <name>". No second source. If the paragraph no longer names a host (the sentence was edited away), the job exits 1 with "writer host not found in triage skill", writes ATTENTION, and touches nothing; a unit test covers it.
3. **Lock.** The job does NOT take `.curated-update.lock`. It checks, without taking, that the lock directory is absent; if present it logs "lock held by <content>" and exits 0. The skill takes and releases its own lock as it does today. A run interrupted by the wall clock leaves the lock exactly as the skill's rule says; the job then writes `~/.agents/knowledge-triage/ATTENTION` with the timestamp and posts one BLOCKED line to `~/.agents/notes/ben-inbox.md` (via note-send `--to ben`); it never clears the lock and skips every later run while ATTENTION exists. Two consecutive runs that find the lock held escalate the same way (ATTENTION plus the ben-inbox line), since a lock nobody releases is the same stall as a timeout. The `--to ben` route is the multi skill's documented one (a BLOCKED to ben is appended to `~/.agents/notes/ben-inbox.md`); the unit test asserts the line lands in a fake ben-inbox. The ATTENTION file and the ben-inbox line both carry the manual recovery command, verbatim: `rmdir ~/.claude/knowledge/.curated-update.lock` (after checking no triage process is running) and then `rm ~/.agents/knowledge-triage/ATTENTION`; Ben runs it, never an agent.
4. **The nested call.** `claude -p` with a prompt that names the triage skill and a cap of 40 oldest notes per run, model `claude-sonnet-5-5`, wall clock 40 min, `--session-id <uuid>` recorded in last-run.json. Flags are pinned by the lane's FIRST step, a probe recorded in the evidence: the nested session must (a) load the user-level triage skill, (b) keep the user permission rules and the secret-guard and git-identity-guard PreToolUse hooks from ~/.claude/settings.json (the distill precedent's `--setting-sources ""` drops them and pairs with `--tools ""`, which would leave triage no tools, so that precedent is NOT copied), (c) not recurse into this job, (d) leave no trace in the notes channel: no line appended to `~/.agents/notes/<day>.md`, `docs/ledger/`, `inboxes.json` or `panes.json` by the nested session's hooks (the nested session has no slug and must not register one), (e) complete one full triage of a scratch store with zero permission denials, adding `--allowedTools` for the exact tools the skill uses if and only if a denial shows up, and pinning that list. The probe runs `claude -p` with candidate flag sets against a scratch store and reports which set satisfies a through e; the spec pins the winner in the record before the builder writes the job. The wall clock kills the whole process tree, not the top pid (`taskkill /T /F /PID` on Windows, the process group on POSIX), and a test with a fake `claude` that spawns a grandchild proves the grandchild dies. The job's environment unsets ANTHROPIC_API_KEY so the plan, not an API key, is billed; the nested run's reported token count is written to last-run.json and the record quotes the first run's.
5. **Publish.** The skill's own allowlisted publication, unchanged. The job only verifies after the run that the dotfiles repo's HEAD moved when DIGEST.md changed, and records the sha; it never runs chezmoi or git itself.
6. **Read-count hygiene.** The triage run's own topic edits must not count as knowledge reads. `scripts/knowledge-counts.mjs` excludes read-log lines whose session id is listed in `~/.agents/knowledge-triage/sessions.json` (appended by the job with the `--session-id` it passed). One test.
7. **Two text amendments, under the tick.** ~/.claude/skills/triage/SKILL.md gains one sentence after :28: "A run started by the knowledge-triage job installed under Ben's decision of <tick date> is Ben asking, for at most 40 notes per run." docs/windows-knowledge-update/README.md:5 gains the same clause. Both live in the chezmoi repo, not this plugin, and neither is on the skill's publish allowlist (which covers knowledge files only), so they get their own commit: the lane's runner, on Windows, under the tick, takes `.curated-update.lock` the way the skill does, runs `chezmoi add --secrets error` on exactly those two files, commits "docs(triage): scheduled runs are Ben asking (decision of <date>)", pushes, verifies the sha on the remote, releases the lock; sha quoted in the record. If a guard refuses the runner, the lead runs the same four commands and says so. Without the tick these lines are not written and the lane is not dispatched.
8. **Measure and prediction.** Readers that exist today: `node scripts/knowledge-count.mjs` on Windows (pending, topics, reads in 7 days) and `~/.agents/knowledge-triage/last-run.json`. last-run.json also records `notesArrived`, the count of inbox notes newer than the previous run's end, so the measure separates the triage rate from the arrival rate (a pending count that does not fall may mean arrivals, not a failing run). `docs/census.md` gets a section "Knowledge triage: fed" naming both, appended (lanes 37 and 38 edit that file too; the section is appended at the end and rebased, never interleaved). Prediction, into the record: each scheduled run lowers Windows pending by at least 30 until fewer than 40 remain (the skill may legitimately leave notes it cannot place; those are the residue, named in DIGEST); DIGEST.md gains dated entries on each run day; topic reads in 7 days on Windows, excluding the job's session, is at least 3 by 2026-10-12 (from 1). Lane 18's prediction ("reads rise from the count line alone by Oct 4") is confounded the day the first run happens; lane 18's checker is not edited by this lane; the record states the confound and the pre-run Windows numbers as the before value, and the decision item asks Ben whether the first run waits until Oct 4.
9. **Kill switches, fail-open.** `~/.agents/no-knowledge-triage` or `~/.agents/ws-off` skips the run (exit 0, logged). A missing skill, an absent Claude CLI, a held lock, ATTENTION present, a non-writer host: exit 0 with the reason, nothing touched. A non-zero nested exit: recorded, nothing else.
10. **Host neutrality, stated.** The runner is the Claude CLI because the triage skill is a Claude skill on this host; a Codex runner (`codex exec` with the mirrored skill) is an explicit unsupported capability in census.md until someone tests it. The lane is Codex-led all the same, as lane 37 is.
