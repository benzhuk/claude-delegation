  rather than forking its regex — the file's own doc comment at mirror-shared-skills.mjs:704-709

  `(tmp|temp|scratchpad|worktrees?|wt-[^/]*)\/`) only matches a temp/worktree segment followed by
  more path; a bare directory whose own last segment IS the worktree name has nothing after it and
  would not match on its own. Confirmed by a failing-then-fixed test run (see below).

  locally since that file doesn't export it).
- `StandardOutput=truncate:<path>` / `StandardError=truncate:<path>` chosen for the systemd unit
  after reading this host's own `man systemd.exec` (systemd.exec(5), the `truncate:path` paragraph:
  "similar to file:path above, but it truncates the file when opening it") — verified against the
  real man page on this machine, not assumed.
- The scheduled command's `--repo <repo>` is written per the seam contract's pinned text, but is
  inert to janitor.mjs's own CLI today (grep confirms no `--repo` parsing exists, and the brief's NOT
  list forbids adding it — only `--host` was in scope). Real repo-targeting for a live run comes from
  each generated unit/task/plist's own WorkingDirectory setting (systemd `WorkingDirectory=`, the
  Windows task's `<WorkingDirectory>`, launchd's `WorkingDirectory` key) — documented at the top of
  install-janitor-timer.mjs and flagged as an open question in the state file, not silently assumed.
- `~/.agents/janitor-repo`'s content shape: per the brief's own instruction not to guess and to "pick
  the simplest reading," implemented as a bare path string (first line, trimmed).
- `installed.json`'s key order (schema, repo, node, hour, scheduler, name) is built literally in that
  order (JS preserves object insertion order) to match the seam contract's shown compact JSON exactly.

   directly defends the reviewer's named attack ("--remove deleting a user's unrelated janitor* unit")
   from the write side as well, at negligible cost.
4. Windows/macOS "truncate per run" is achieved via a shell wrapper (`cmd /c ... > log 2>&1` /
   `/bin/sh -c '... > log 2>&1'`) rather than a native redirect, since Task Scheduler's Exec action
   has no stdout/stderr element and launchd's StandardOutPath/StandardErrorPath append rather than
   truncate (per my reading — not verified live, since neither binary exists on this host). Flagged,
   not guessed-and-buried.
5. Live-verification step 3 redirected `--record`'s output directory explicitly (a scratch dir)
   rather than using the pinned bare `--record` (which would resolve to the watched repo's own
   `docs/work/evidence/janitor/`) — a deliberate, noted choice to avoid writing into a shared tracked
   repo during a builder's own verification pass. The generated/installed command itself (in
   installed.json and the unit file) is still the exact pinned bare `--record --repo <repo>` form;
   only my manual by-hand run used the optional path argument `--record` already supports.
