## Fix 1: `--no-repo` means "not checked", never "missing" (work lost or stalled)

Observed 2026-09-27 5:42 PM New York: the lead's PostToolUse inbox hook printed `[skills-a-codex-census-10] points at docs/notes/skills-a-codex-census-10.md, which is not on this machine` while the packet sat at that path in the main checkout, written by note-send itself. Cause: `hooks/multi-inbox.js:336` (and `multi-codex-hook.mjs:162` for Codex) passes `--no-repo` on PostToolUse by design; `note-inbox.mjs:212` then builds no repo source; `packetLocation` (note-inbox.mjs:330-337) returns `exists: false` with nothing checked; line 268 pushes that default as a problem, `multi-hook-core.mjs:58-60` prints problems verbatim, and the per-note summary at `multi-hook-core.mjs:49` and `formatInbox` at `note-inbox.mjs:366` both render a falsy value as `packet MISSING`. The lead spent two research agents on a defect that did not exist.

Pinned rule, three-valued: `packetLocation` returns `exists: null` when no repo source was consulted (`--no-repo`, or no repo resolved); the JSON carries `packetExists: null` and `packetChecked: false` for such notes. The problem at note-inbox.mjs:268 is pushed only when `packetExists === false`. Both renderers test strictly: `packetExists === true` prints `(packet: <path>)`, `=== false` prints `(packet MISSING: <details>)`, `null` prints `(packet: <details>, not checked here)`; that is `summarise` in multi-hook-core.mjs:49 and `formatInbox` in note-inbox.mjs:366. Existing consumers already pass `packetExists: null` only with `details: null` (multi-hook-core.test.mjs:27, multi-codex-hook.test.mjs:60) and are unaffected. Nothing else changes: the next UserPromptSubmit or Stop read runs with the repo source and reports the truth.

## Fix 2: the skill states how a Codex peer receives (work lost or stalled)

Observed 2026-09-27: three notes to a Codex peer, each queued with `delivered: true` at 4:35, 4:46 and 5:07 PM New York, were acted on at 5:41 to 5:49 PM; the lead read the silence as lost notes and re-asked. Cause is by design (codex-notes-research-report.md section A; inbox-codex.mjs:7 and :22): `codex queue` stores a row that the Codex TUI starts as a turn only when the current turn ends; a Codex turn is atomic and nothing drains the queue inside it. `delivered to null` is cosmetic: `handle` is null whenever the inbox path skips pane resolution (note-send.mjs:831, 890-894).

Pinned text, one paragraph placed directly after the idle bullet at SKILL.md:112-114 (which already says "Codex runs it as its next turn"; do not restate that clause): "A Codex peer sees nothing mid-turn. `codex queue` stores the row at once (`delivered: true`) and the Codex TUI starts it only when the current turn ends, however long that turn runs. Silence from a Codex peer after a delivered note means it is still in a turn. Re-asking queues a second turn behind the first; check the ledger for its ACK instead. `delivered to null` on a sender's receipt is the inbox path: no pane was resolved, so there is no handle to print."
