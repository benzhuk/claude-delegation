## The change (contracts.md R1, exact)

In `buildFlushStatus` (note-flush.mjs, currently ~line 299), extend the human `line` and
the `json` return to report registered pickup's existing state, using ONLY:
- `heartbeat.pickup` when present (an object `{ at, code, ordinal }` written by
  `annotatePickup`) — append `; pickup: <code> <age>` to the line, where `<age>` is
  computed from `heartbeat.pickup.at` the same way `ageS` is already computed from
  `heartbeat.at` (`Date.parse` then seconds elapsed against `now`), formatted consistently
  with the existing `${ageS}s` style used elsewhere in this function.
- Else, when the registration file does not exist: `; pickup: not registered on this
  host`, decided by exactly ONE `lstat` of `<agentsHome>/ws/decisions-pickup/registrations.json`
  where `agentsHome = path.resolve(home, '.agents')` — mirror `runPostFlushPickup`'s own
  existence check (ENOENT/ENOTDIR = not configured; any other lstat result, including a
  successful stat of a symlink/garbage file, counts as "configured" for THIS purpose —
  ruling on scout-M2.md's third open question: this status line does existence-only
  checking, exactly like `runPostFlushPickup` does before it even tries to parse the file;
  do not parse or validate the registration file's contents here — that would require
  importing `decisions-pickup.mjs` internals, which is out of scope).
- Else, when `ws-off` or `ws-off-decisions` exists (checked the same way
  `runPostFlushPickup` does, via the same `switchActive`-shaped lstat-based check): `;
  pickup: disabled (<switch>)`. Ruling on scout-M2.md's second open question: check
  `ws-off` first; if it exists, name it (`disabled (ws-off)`); else if
  `ws-off-decisions` exists, name it (`disabled (ws-off-decisions)`). Only one name is
  ever reported even if both exist.
- Ruling on scout-M2.md's first open question: append the `; pickup: ...` suffix on BOTH
  return branches of `buildFlushStatus` — the missing-heartbeat early return (append after
  whichever of its two existing lines fires) AND the normal fresh/stale return. A missing
  or unreadable flush-last.json says nothing about whether pickup is registered; both are
  independently checkable and both should report it.
- `--status --json` gains the same information as a `pickup` field — object or string,
  your choice; document the exact shape in a comment above `buildFlushStatus` and in your
  test names. Do not add this key when there is truly nothing to report only if that
  breaks a JSON-shape rule elsewhere — there isn't one; add it unconditionally on every
  call (see the regression risk below on the existing `deepEqual` tests).
- No new log line, no new state file, no new kill-switch name, no new page read, no new

  existence, kill-switch files' existence) that `buildFlushStatus` already has access to

## Concrete regression risk (scout-M2.md section 3 — read before writing code)

Two existing tests do `assert.deepEqual(status.json, {missing: true, unreadable: false,
age_s: null, timer_age_s: null, stale: true})` and the corrupt-heartbeat equivalent
(`unreadable: true`). Adding a `pickup` key to the json return unconditionally breaks
these two `deepEqual` calls unless you either (a) update those two existing assertions to
include the new `pickup` key's expected value for a fixture with no registration file
present (most likely `pickup: 'not registered on this host'` or your chosen object
equivalent), or (b) both are equally valid — pick one, document your choice as a comment,
and make the update. Do not leave these two tests broken; they are IN your territory's own
test file, not a foreign gate.
