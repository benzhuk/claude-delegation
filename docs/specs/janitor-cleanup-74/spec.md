# Lane 74: cleanup that cannot recur (10/1, opened after Ben's janitor question)

Ben, 10/1 about 8:50 PM: "agents were leaving hundreds of worktrees in all kind of places, and dropping temp files and uncommitted code all over. does janitor fixx all the issues we cleaned up so they can never happen again?" Ben, 9/30: "I never wanted that to happen and never want it to happen again". Evidence: docs/work/evidence/2026-10-01-cleanup-vs-janitor.md (every class cleaned on 9/29 and 9/30 against what prevents or cleans it today) and 2026-10-01-detritus-census.md. Measure: work lost or stalled (a clean checkout and no lost uncommitted code), hours (no hand cleanup days).

The finding: the janitor removes one class only, a clean, merged, idle worktree or merged local branch of the one repo it is pinned to, and it has removed nothing since it was scheduled. Everything else in the cleanup (dirty worktrees with uncommitted code, worktrees of other repos and in other places, unmerged branches, deregistered folders, temp files, untracked packets, detached and dirty checkouts on other hosts) has no owner. The new-worktree guard (lane 65) is on main and installed nowhere.

## Scope, pinned
1. Nothing is created where it cannot be cleaned. The guard from lane 65 stays the only rule for where a worktree goes. The build loop commits a builder's territory to the lane branch at the end of every phase and before any report, so uncommitted code never outlives a phase. A builder or runner that dies leaves committed work.
2. Every worktree has an owner or is an orphan. A worktree is owned when an open record's `Worktree:` line names it. The janitor's roots are a list (default: every git repo under `~/Code`, `<repo>/.claude/worktrees`, the session Temp scratch root, `orca/workspaces`, `/var/tmp/lane-*`), not one pinned repo. It lists registered worktrees per repo and also folders under the roots that hold a `.git` file or dir and are not registered (deregistered leftovers).
3. ARCHIVE then remove, never delete work. A dirty worktree whose record is accepted or closed, or that has no record, and that has been idle 24 h: the janitor commits everything in it to `archive/<lane-or-folder>-<shortsha>`, pushes that branch to origin, then removes the worktree. An unmerged local-only branch with no open record gets the same: pushed as `archive/...`, then deleted locally. Merged origin branches are deleted daily. This is the automation of what the 9/30 cleanup did by hand (wt-archive-pass.sh).
4. Closeout is automatic. The merge step of the build loop runs `work-record close --closeout` for the lane, which removes its worktree, local and origin branch and scratch dir. A lane that lands leaves nothing.
5. Nothing of the plugin's own lands untracked in a checkout. Peer packets (`docs/notes/<slug>-*.md` and friends) move to `~/.agents/notes/packets/<repo-name>/` with the ledger pointing at them; pickup pointer files and `docs/work/evidence/janitor/*.json` move to `~/.agents/`; `docs/ledger/` is either tracked (committed by the flusher daily) or moved out, the lane rules which and says why. The janitor reports any untracked file in a durable checkout older than 7 days by path.
6. Hosts. Install of the plugin re-registers the janitor timer from the installed release on every host, so a stale timer cannot keep running old code (today Netcup and Hetzner run 0.20.14 janitors). The drift log fix (lane 65 item 7) is in the same release.
7. Policy table for Ben, one tick before the new classes act: a page item lists each class with its action (archive then remove, delete, report) and the roots. Until the tick, the new classes run in report mode and print what they would do. The existing SAFE class keeps acting.
8. Tests for 1 to 6 against fixtures, including a dirty worktree with untracked files, a deregistered folder, a second repo under the roots, and a dying builder with uncommitted edits.
Not in scope: BTO repos (Ben: "leave BTO to BTO"), the dotfiles repo, orphan processes (a separate small lane if Ben wants it), any `rm` by an agent.
